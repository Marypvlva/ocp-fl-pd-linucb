# Прогон на Yandex Cloud: распределённый стенд OCP-FL + AF-PD-LinUCB

Ниже описан порядок развёртывания стенда, проверки его исправности и запуска парного живого исследования. Все команды готовы к копированию. Исследование можно продолжить после остановки ВМ: уже завершённые эпизоды пропускаются.

## Что проверяет облачный прогон

Симуляционное исследование 3 показывает преимущество метода на 96 свежих мирах в 17 ячейках. На локальном стенде видно, что живой протокол воспроизводит результаты замороженного мира (fidelity = 1.0). Облачный прогон закрывает оставшийся вопрос: сохраняется ли преимущество, когда роли работают на отдельных машинах в трёх зонах доступности. Отказы при этом настоящие:

- закрытый порт (`refuse`) или зависший узел (`silent`);
- реальные задержки;
- сравнение дедлайнов по синхронизированным часам (NTP/chrony);
- полный протокол на каждом раунде: commit–reveal в EVM, BLS-маяк, вычисление градиентов, агрегация на edge, проверка проекции или подписанного обновления.

Топология (по умолчанию, `variables.tf`):

```
ru-central1-a: coordinator (16 vCPU/32 GB, публичный IP)  edge-0, edge-1 (основная полоса)  worker-0, worker-3
ru-central1-b: edge-2 (резервная полоса)                    worker-1
ru-central1-d: edge-3 (резервная полоса)                    worker-2
```

9 ролей-клиентов распределяются по worker-ВМ по кругу, поэтому соседние клиенты оказываются в разных зонах. Основная полоса (e0/e1) расположена в зоне координатора, резервная (e2/e3) — в других доменах отказа. Если резервную полосу нужно сделать «региональной», задайте `backup_edge_netem_ms = 20`.

## 0. Что нужно заранее (≈15 мин)

1. Каталог (folder) в Yandex Cloud с привязанным платёжным аккаунтом.
2. Квоты: не меньше 40 vCPU и 56 ГБ RAM на standard-v3, 9 ВМ, 1 публичный IP, 1 NAT-шлюз.
3. На ноутбуке: `yc` CLI, Terraform ≥ 1.5, `jq`, `rsync` и ssh-agent с вашим ключом (`ssh-add ~/.ssh/id_ed25519`).
4. Авторизация Terraform: `export YC_TOKEN=$(yc iam create-token)`.

## 1. Поднять стенд (≈10 мин)

```bash
cd adaptive_planning/deploy/yandex
cp terraform.tfvars.example terraform.tfvars   # впишите cloud_id, folder_id, свой IP/32
bash stand.sh up        # terraform apply + inventory.json + placement.json
bash stand.sh push      # копирует проект на координатор
bash stand.sh ssh       # заходит на координатор с агентом (ssh -A)
```

## 2. Подготовить ВМ (на координаторе, ≈10 мин)

```bash
cd ~/adaptive_planning
~/.local/bin/uv venv --python 3.13 .venv
~/.local/bin/uv pip install --python .venv/bin/python -r requirements-lock.txt
~/.local/bin/uv pip install --python .venv/bin/python --no-deps -e .
bash deploy/yandex/bootstrap.sh deploy/yandex/inventory.json
```

`bootstrap.sh` выполняет четыре шага:

- ждёт окончания cloud-init;
- создаёт внутренний ключ стенда `~/.ssh/stand`, чтобы исследование продолжалось после отключения вашего агента;
- разносит проект и окружение Python 3.13 (из lock-файла) по всем ВМ;
- записывает смещение часов каждой ВМ в `clock_check.txt`.

**Критерий:** все смещения меньше 10 мс. Дедлайн раунда — 3 с, таймаут RPC — 2 с.

## 3. Приёмка стенда и запуск исследования (≈3 ч)

```bash
bash deploy/yandex/run_on_coordinator.sh study_cloud 12
tail -f study_cloud/progress.log
```

Скрипт запускает `stand_check` дважды — с отказами `refuse` и `silent`. Приёмка требует, чтобы выполнялись все условия:

- все здоровые раунды принимаются;
- если основная edge отключена по-настоящему, F-раунд отклоняется и модель не меняется, а R-раунд спасает резервная полоса;
- при двойном отказе раунд отклоняется;
- отсутствие проекции блокирует P, но не B;
- после раунда ворота снова открываются.

Только после этого замораживается `plan.json` и запускается парное исследование.

Параметры исследования:

- ячейки: S11, D2, D6, S4_n8;
- 16 свежих сидов (520000…);
- горизонт 240 раундов;
- политики AF_L, greedy_dual, rescue_forecast_orig, PD_original;
- порядок политик внутри сида случайный.

Всего 256 эпизодов, 12 из них идут параллельно.

Если ВМ была остановлена (например, прерываемая), повторите ту же команду: готовые эпизоды будут пропущены.

## 4. Итоги и аудит

```bash
.venv/bin/python deploy/live_study.py summarize --out study_cloud   # парные разности, бутстреп, Wilcoxon+Holm, fidelity
.venv/bin/python deploy/audit_study.py study_cloud                  # независимый аудит каждого эпизода
```

На ноутбуке:

```bash
bash deploy/yandex/stand.sh fetch study_cloud
bash deploy/yandex/stand.sh down
```

**Обязательно выполните `down`, иначе ВМ продолжат тарифицироваться.**

Прогон считается успешным, если выполнено всё:

1. Аудит пройден для 100 % эпизодов.
2. Средняя fidelity не меньше 0.99. Отклонения разрешены только за счёт настоящих таймаутов; их видно в `errors` раунда.
3. В каждой ячейке разность AF_L − greedy_dual положительна и значима после поправки Holm. Направление и порядок величины должны совпадать с симуляцией (см. `study3/RESULTS3.md`).

## Ограничения, которые нужно держать в голове

- Жёсткий бюджет байтов (`app_byte_budget`) использует общую память и между хостами недоступен. Байты измеряются на каждой роли и собираются за раунд. Бюджет трафика в планировщике — прогнозный, как и в симуляции.
- EVM и BLS-маяк работают локально на координаторе (EthereumTester/PyEVM, тестовый маяк). Распределённый консенсус не проверяется: это свойство OCP-FL, а не планировщика.
- Кадры аутентифицированы (HMAC), но не зашифрованы. Стенд работает внутри приватной сети VPC: группа безопасности пропускает трафик только между ВМ стенда и SSH с вашего IP.
- Живой сэмплер поддерживает не больше 9 клиентов (встроенные тестовые аккаунты). Ячейки с 16 клиентами проверяются только в симуляции.

## Если что-то пошло не так

| Симптом | Причина и действие |
|---|---|
| `Startup timeout: wN` | Нет окружения на ВМ: перезапустите `bootstrap.sh`. Проверка: `ssh <ip> ~/adaptive_planning/.venv/bin/python -m adaptive_planning.node </dev/null` |
| `stand check: FAIL` | Откройте `study_cloud/stand_check_*.json`. Посмотрите поле `errors` и `control_rtt_ms` (≫ 50 мс означает перегрузку) |
| много `failed` в progress.log | Ошибки лежат в `study_cloud/errors/*.txt`. Уменьшите `--parallel`. Проверьте `ulimit -n` и `MaxSessions` |
| смещение часов > 10 мс | `sudo chronyc makestep` на ВМ; повторите проверку |
