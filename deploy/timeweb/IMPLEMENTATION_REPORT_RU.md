# Реализация Collector v3 для Timeweb Cloud

База — v0.5.0, commit 768a83b7a41d79d6574a18b4b4f19765250fe34c. Текущая версия программного комплекта — v0.6.0. В репозитории сохранены исходные матрицы и результаты исследования v3. Новых результатов реального Timeweb-стенда в поставке нет.

## Выполненные изменения

1. `bootstrap.sh` устанавливает Python 3.13.7 на Ubuntu 24.04 x86_64 через uv 0.9.11, системные средства связи и chrony. Отдельный Linux lock с SHA-256 пакетов получен и установлен в Ubuntu 24.04 x86_64 GitHub Actions. Системный Python сохраняется, неподходящая виртуальная среда архивируется.
2. `live.py --plan` подключает `distributed_live.py` и актуальный `model.Policy` к `RemoteCluster`. Роли запускаются с координатора через SSH. Старый вход локального воспроизведения сохранён.
3. `distributed_control.py` предоставляет общий атомарный SQLite-журнал квот, аутентификацию HMAC поверх TLS, полное резервирование кадра до отправки, идемпотентный учёт и консервативную обработку потери отправителя. Все узлы и координатор используют один сервис. Возвращение метрик больше не зависит от реализации локального SharedByteBudget.
4. `lease_guard.py` на каждом узле сверяет контракт и конфигурацию, состав, маску, окно, блок и дайджест выдачи. До подтверждения всех ролей передача раунда не начинается. Невыбранный работник и неоплаченный collector получают отказ. Контрольные запросы с round=0 отделены от прикладного трафика.
5. В режиме natural не передаются эмулированные времена. Контролируемые отказы создаются отдельным планом и маркируются. Старое воспроизведение матриц остаётся отдельным входом.
6. Журналируется полное время от начала церемонии до фиксации модели, а также составляющие финальности, брони, сетевого исполнения, учёта и фиксации. В telemetry добавлено ожидание серверных очередей. Записываются исходная/предыдущая/новая модель, открытые ключи и подписанные ответы для независимого аудита.
7. Подготовлены пилот на пяти ВМ и профиль подтверждающего опыта на девяти. Для внешнего консенсуса нужен предоставленный оператором RPC, поддерживающий finalized. Узлы читают его напрямую, а runner ждёт finalized для брони и модели. Создание source-контракта вынесено в отдельный операторский инструмент с явным --execute.
8. `manage.py` выполняет развёртывание, peer-to-peer диагностику и проверку синхронизации, фиксирует планы и запускает опыты. `summarize.py` аудирует журналы и считает разницы по целым блокам. `export.py` выдаёт результаты через HTTPS с паролем. Работа предусмотрена из браузерной консоли координатора.

## Ограничения, существенные для статьи

Доступа к действующим Timeweb-ВМ в этой сессии нет. Межхостовая пропускная способность, естественные задержки, доступность peer SSH, clock skew и влияние характеристик ВМ ещё требуют реального прогона. Ни бесплатные, ни платные облачные ресурсы средствами развёртывания автоматически не создаются.

Сервис допуска — доверенный координатор с единой точкой отказа. Он ограничивает прикладные кадры честно исполняющих протокол узлов. Контрольный HTTPS, SSH, RPC, начальное размещение данных, заголовки и повторные передачи ядра находятся вне прикладного байтового бюджета. Злоумышленный узел с произвольным сетевым кодом требует контроля ОС/сети. Потерянная отправка может оставить полную бронь. Автоматическое освобождение по времени отсутствует, что обеспечивает консервативный предел.

Локальная EVM обслуживается через доверенный HTTPS-мост координатора и явно помечена local_evm. Её подтверждения не измеряют внешний консенсус. Внешний RPC-режим требует реальной сети с finalized, корректных TLS RPC и предоставленных аккаунтов. На каждом узле считывается и проверяется один и тот же canonical contract state. Независимая проверка подписей валидаторов вне доверенного RPC не реализована. Внешний консенсус не запускался в поставленных проверках.

Реальный drand меняет случайность между церемониями. Поэтому внешний режим ограничен одним эпизодом с одной политикой, а парные сетевые сравнения используют одинаковые детерминированные исследовательские составы локальной EVM. Естественные сетевые исходы всё равно меняются во времени. План фиксирует рандомизированное последовательное crossover-сравнение, а статистика условна на этих хостах и периодах.

При аварии координатора незавершённый эпизод автоматически не возобновляется. Сохраняются квоты и журнал ошибки, а повторный расход с тем же именем блокируется. Завершённые эпизоды допускают пропуск при продолжении. Неполные эпизоды явно перечисляются в summary. Для независимого повторения нужен новый план и каталог с сохранением исходного выпадения.

Число подтверждающих блоков в профиле является настройкой нагрузки. Достаточность для минимального полезного эффекта определяется по пилотной дисперсии до сбора подтверждающей выборки. Добавленная инфраструктура сама по себе не устанавливает преимущество UCB-бонуса над сильными именными контролями.
