# Collector v3 на Timeweb Cloud

Эта инструкция выполняется в браузерной консоли координатора. Исходная точка — Ubuntu 24.04 x86_64 в Амстердаме, каталог `/opt/research/ocp-fl-pd-linucb`. SSH с Mac для управления стендом и скачивания результатов не требуется. Репозиторий содержит реализацию распределённого пути. Реальные результаты появятся после запуска на ваших ВМ.

## 1. Выбрать размер стенда

| Назначение | ВМ | Предлагаемые характеристики |
| --- | --- | --- |
| Минимальный сетевой пилот | 5 всего | существующий координатор 1 vCPU / 2 ГБ / 30 ГБ, две worker-ВМ по 1 vCPU / 2 ГБ, две gateway-ВМ по 1 vCPU / 2 ГБ |
| Подтверждающий сетевой стенд | 9 всего | координатор 2 vCPU / 4 ГБ, четыре worker-ВМ по 2 vCPU / 4 ГБ, четыре gateway-ВМ по 1 vCPU / 2 ГБ; диски от 30 ГБ |

Пилот использует четыре работника на двух физических ВМ и четыре логических шлюза на двух ВМ. Он проверяет передачу, квоты, доступность и разброс времени. Совместное размещение шлюзов создаёт зависимые отказы, это фиксируется в плане. Для подтверждающего опыта используются 16 работников на четырёх ВМ и четыре раздельных шлюза. Так различаются пути и физические домены отказа. Характеристики являются стартовой инженерной оценкой. По пилоту проверьте RSS, загрузку и p95 времени, затем зафиксируйте окончательную конфигурацию до подтверждающих прогонов.

Программа не создаёт ВМ. Дополнительные машины создаёт пользователь в панели после проверки стоимости. Для измерения естественной неоднородности разместите шлюзы в заранее выбранных разных локациях. Сначала проверьте доступные локации и соединения в своём аккаунте. Начальный профиль подтверждающего опыта содержит 12 блоков по 480 раундов на политику. Его статистическую мощность ещё следует оценить по дисперсии пилота и зафиксировать новый план до просмотра подтверждающих результатов.

Все команды ниже вводятся на координаторе под root. Браузерная консоль доступна в панели Timeweb в карточке сервера. [Описание консоли](https://timeweb.cloud/docs/cloud-servers/manage-servers/console).

## 2. Получить версию и установить Python 3.13

В браузерной консоли координатора

```bash
cd /opt/research/ocp-fl-pd-linucb
git status --short
git fetch origin --tags
git switch --detach v0.6.0
bash deploy/timeweb/bootstrap.sh
.venv/bin/python --version
```

Ожидается Python 3.13.7. Если git сообщает о ваших изменённых файлах, сохраните их в отдельную копию перед переключением версии. Bootstrap устанавливает системные пакеты, chrony, uv 0.9.11, управляемый Python и зависимости из отдельного `requirements-linux-x86_64.lock` с проверкой хешей. Системный Python 3.12 остаётся доступен Ubuntu. Предыдущая виртуальная среда другой версии сохраняется под именем `.venv-before-timeweb-*`. Журнал проверки среды находится в `results/bootstrap/`.

Lock-файл получен на Ubuntu 24.04 x86_64 и установлен с `--require-hashes`. Проверка происхождения записана в `linux-lock-verification.txt`. [Установка Python через uv](https://docs.astral.sh/uv/guides/install-python/).

## 3. Записать IP-адреса и создать ключ координатора

В панели вручную создайте четыре дополнительные ВМ пилота с Ubuntu 24.04. В браузерной консоли координатора подставьте реальные IP вместо примеров TEST-NET

```bash
cd /opt/research/ocp-fl-pd-linucb
COORDINATOR=203.0.113.10
WORKER_A=203.0.113.11
WORKER_B=203.0.113.12
GATEWAY_A=203.0.113.13
GATEWAY_B=203.0.113.14
.venv/bin/python deploy/timeweb/manage.py init \
  --coordinator "$COORDINATOR" \
  --workers "$WORKER_A" "$WORKER_B" \
  --gateways "$GATEWAY_A" "$GATEWAY_A" "$GATEWAY_B" "$GATEWAY_B"
```

Программа создаст локальный каталог `deploy/timeweb/state/`, SSH-ключ координатора и TLS-сертификат с IP координатора. Напечатается строка публичного SSH-ключа, начинающаяся с `ssh-ed25519`. Скопируйте её. Приватный ключ остаётся на координаторе.

В браузерной консоли КАЖДОЙ из пяти ВМ, включая координатор, выполните

```bash
mkdir -p /root/.ssh
chmod 700 /root/.ssh
cat >> /root/.ssh/authorized_keys <<'KEY'
ВСТАВЬТЕ_СЮДА_ОДНУ_СТРОКУ_ПУБЛИЧНОГО_КЛЮЧА
KEY
chmod 600 /root/.ssh/authorized_keys
```

Это устанавливает доступ координатора к узлам. Пароли ВМ вводить в репозиторий не требуется. Убедитесь, что OpenSSH на каждой ВМ запущен командой `systemctl status ssh`. При необходимости выполните `systemctl enable --now ssh`.

## 4. Открыть соединения между ВМ

В панели Timeweb настройте сетевые правила и при необходимости локальный firewall. Для всех узлов стенда разрешите

- TCP 22 на всех узлах от IP координатора;
- TCP 23000–23019 между IP всех узлов стенда;
- TCP 23100 между ними для диагностики;
- TCP 9443 на координаторе от IP всех узлов стенда;
- исходящий HTTPS 443 для GitHub, пакетов и маяка;
- DNS и синхронизацию времени NTP через UDP 123.

Публичный экспорт результатов использует отдельный TCP 8443 на координаторе. Его разрешают только с IP пользователя на время скачивания. При использовании приватной сети передавайте доступные в ней адреса. Доступность приватных сетей зависит от линейки серверов. [Сеть](https://timeweb.cloud/docs/cloud-servers/manage-servers/network), [ограничения сервиса](https://timeweb.cloud/docs/cloud-servers/limitations).

Проверьте локальные правила командой `ufw status verbose`. Скрипт не отключает firewall. SSH с Mac может оставаться недоступным, но SSH с координатора к ВМ должен работать.

Вернитесь в консоль координатора. Для каждого адреса из inventory выполните первый вход

```bash
ssh -i deploy/timeweb/state/coordinator_key root@203.0.113.11 true
```

Заменяйте IP. Перед ответом `yes` сравните отпечаток ключа сервера с выводом следующей команды в браузерной консоли соответствующей ВМ

```bash
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
```

Повторите для самого координатора и всех worker/gateway ВМ. Далее автоматизация использует только уже известные host keys. Если соединение отклонено, проверьте правило TCP 22, `systemctl status ssh`, IP и `authorized_keys` на соответствующей ВМ. [Подключение SSH](https://timeweb.cloud/docs/unix-guides/ssh).

## 5. Автоматически развернуть и проверить сеть

На координаторе

```bash
cd /opt/research/ocp-fl-pd-linucb
.venv/bin/python deploy/timeweb/manage.py deploy
.venv/bin/python deploy/timeweb/manage.py diagnose
```

Deploy последовательно копирует текущие исходники и публичный TLS-сертификат, устанавливает Python 3.13 и Linux lock на узлах. Ключ координатора, каталог результатов и секреты TLS не пересылаются. Diagnose требует синхронизации chrony в пределах 5 мс, запускает временный TCP-пробник и проверяет все направления между ВМ. Результаты сохраняются в `state/diagnostics.json`. Требование 5 мс относится к сопоставимости окон 80–200 мс, его нельзя считать доказательством нулевой погрешности часов. Перед каждым опытом диагностику повторяют. Если chrony ещё не синхронизировался, подождите и повторите diagnose.

## 7. Зафиксировать и запустить межхостовой пилот

На координаторе

```bash
.venv/bin/python deploy/timeweb/manage.py plan \
  --profile pilot --out results/timeweb-pilot
cat results/timeweb-pilot/plan.json
```

План содержит исходники с SHA-256, commit, начальную историю, настройки политик, одинаковые квоты, раскладку ВМ, порядок сравнения, сиды и дедлайны. `plan.sha256` выявляет изменение плана. Сетевой режим по умолчанию `natural`, `emulated_link_ms` отсутствует. Все политики обучаются с пустой историей, одинаковой исходной моделью и апрельской калибровкой. Внутри блока используются одни составы, а последовательность политик рандомизирована. Естественная сеть меняется во времени, одинаковые физические исходы разных политик обещать невозможно.

Для первого технического smoke можно сначала создать отдельный короткий план

```bash
.venv/bin/python deploy/timeweb/manage.py plan --profile pilot \
  --out results/timeweb-smoke --rounds 4 --seeds 81100 --modes joint
.venv/bin/python deploy/timeweb/manage.py run --out results/timeweb-smoke
.venv/bin/python deploy/timeweb/summarize.py results/timeweb-smoke
```

Для полного пилота откройте tmux, чтобы запуск продолжался при закрытии браузера

```bash
tmux new -s collector
cd /opt/research/ocp-fl-pd-linucb
.venv/bin/python deploy/timeweb/manage.py diagnose
.venv/bin/python deploy/timeweb/manage.py run --out results/timeweb-pilot \
  2>&1 | tee results/timeweb-pilot/console.log
.venv/bin/python deploy/timeweb/summarize.py results/timeweb-pilot
```

Отсоединиться от tmux — Ctrl+B, затем D. Вернуться — `tmux attach -t collector`. Run обновляет диагностический снимок, проверяет неизменность плана, запускает роли по SSH и последовательно исполняет политики. В коротких/полных эпизодах все отправители резервируют полный кадр до `send`. При пропадании сервиса новые передачи прекращаются. SQLite сохраняет незавершённые брони, предотвращая перерасход после сбоя. Сервис представляет единую доверенную точку допуска, это влияет на задержку и доступность. Байтовый бюджет охватывает прикладные кадры. TCP/IP-заголовки, retransmit ядра, SSH, TLS-служба контроля и EVM RPC находятся вне этого счётчика.

Каждый worker и gateway сам читает и проверяет состояние CollectorLeases. В пилоте он использует HTTPS-мост к локальной исследовательской EVM. Проверяются код, chain ID, адреса, конфигурация, исходный состав, маска, окно, дайджест и канонический блок разрешения. Общее доверие к координатору такого моста записано в журнале как `local_evm`.

## 8. Контролируемые нарушения и подтверждающий опыт

Контролируемые отказы исполняются отдельным режимом с собственным планом

```bash
.venv/bin/python deploy/timeweb/manage.py plan --profile pilot \
  --network-mode controlled --out results/timeweb-controlled
.venv/bin/python deploy/timeweb/manage.py run --out results/timeweb-controlled
```

В каждом пятом раунде отключается один gateway-процесс. Это отмечается в метриках. Здесь по-прежнему отсутствует подстановка RTT из матриц. Архивные эмуляции версии 0.5.0 доступны через прежний вход live.py и сохраняют прежнюю маркировку.

Для подтверждающего опыта используйте четыре разных адреса gateway и четыре worker-адреса в новой раскладке. Сохраните каталог state пилота под другим именем, заново выполните init и шаги 3–5. Создайте новый план с `--profile confirmatory --out results/timeweb-confirmatory`. Его исходные численность и длительность задают повторяемую нагрузку. По дисперсии пилота заранее установите достаточное число блоков, при необходимости через `--seeds`, и фиксируйте обоснование до получения результатов. Несколько раундов одной ВМ не являются независимыми облачными репликациями.

## 9. Реальная распределённая финальность

Локальная EVM пилота подтверждает только исполнение логики и канонические локальные блоки. Полное время каждого раунда всё равно измеряется от начала церемонии до финальной записи модели. Отдельно сохраняются время состава/финальности, бронирования/проверки на узлах, передачи/верификации/обновления, учёта и фиксации модели. Суммарное ожидание очередей потоков серверов также находится в telemetry.

Для измерения консенсусной финальности требуется уже предоставленный оператором HTTPS RPC реальной сети с поддержкой тега `finalized`. Возможный отдельный исследовательский стенд — четыре валидатора BFT с кворумом три при допущении одного неисправного. Тогда к сетевому стенду добавляются четыре ВМ, всего 13. Готовую существующую консенсусную сеть можно использовать без этих дополнительных ВМ. Код в этом репозитории не создаёт и не настраивает валидаторов или платные ресурсы.

Внешний режим читает контракт непосредственно на каждой роли и ждёт, пока блок бронирования и модели попадёт под `finalized`, дополнительно выдерживая глубину подтверждения. Доверие к корректности TLS RPC остаётся явным. Без поддержки finalized запуск прекращается. Реальный внешний консенсус в поставленных проверках не измерялся.

Сначала на уже управляемой оператором тестовой сети подготовьте отдельные аккаунты для oracle и каждого клиента. Они должны иметь необходимые для тестовой сети средства. Оператор может предоставить разблокированные аккаунты в закрытом RPC или указать список приватных ключей в переменной `OCP_SIGNING_KEYS` текущей консоли, без записи в файлы и Git. RPC должен быть доступен всем участникам, а его TLS-сертификат — доверенным системе.

`chain_setup.py --help` описывает создание source-контракта на этой предоставленной сети. Без `--execute` выполняются только чтения. Пример, где все значения заменяются вашими тестовыми реквизитами

```bash
.venv/bin/python deploy/timeweb/chain_setup.py \
  --rpc https://RPC_ВАШЕЙ_ТЕСТОВОЙ_СЕТИ --oracle 0xORACLE \
  --clients 0xCLIENT0 0xCLIENT1 0xCLIENT2 0xCLIENT3 --k 2 \
  --out deploy/timeweb/state/chain.json --execute
```

Создайте новый внешний план с одним сидом и одной политикой, например `--chain-mode external_rpc --seeds 81201 --modes joint`. Запустите его через `manage.py run --out ПАПКА --chain-config deploy/timeweb/state/chain.json`. Потребуется новый source-контракт для нового эпизода. Реальный маяк drand меняет случайность между последовательными церемониями, поэтому внешние эпизоды этим способом не образуют идентичные парные составы. Код ограничивает этот режим одной политикой и одним сидом. Сетевые парные сравнения и тест реальной финальности следует публиковать с соответствующими разными основаниями сравнения.

## 10. Сбои и выгрузка

Каждый завершённый раунд пишется атомарным JSON. Подписи ответов и открытые ключи работников сохраняются для независимой проверки. Состояние квот лежит в budget.sqlite. При незавершённом эпизоде сохраняется failure.json и блокируются автоматический сброс бюджета и перезапуск эпизода с тем же именем. Не удаляйте эти материалы. Продолжение уже завершённых эпизодов допускается, а для повторения прерванного опыта создайте новый заранее обозначенный план с новой папкой и сохраните исходный эпизод как выпадение.

Если процесс был убит, RUNNING может остаться. Перед очисткой убедитесь по `ps -ef`, что координатор и его SSH-роли завершены. Повтор запуска с тем же каталогом не восстановит незавершённую локальную EVM, он выдаст явную ошибку. Это ограничение защищает от повторного расходования квоты после сбоя.

Проверка и HTTPS-выгрузка описаны пошагово в [HTTPS_RESULTS_RU.md](HTTPS_RESULTS_RU.md). Summary проверяет полноту всех эпизодов, исходные модели, составы, подписи, квоты и счётчики. Интервалы строятся по целым seed/time-блокам. Вывод пилота ограничен выбранными хостами и периодом наблюдения. Для статьи сохраняйте исходный план, commit, журнал диагностики и все раунды, включая неудачные.
