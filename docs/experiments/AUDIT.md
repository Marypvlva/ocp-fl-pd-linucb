# Технический аудит и продолжение проекта — 27 октября 2026

## Фактическое исходное состояние

В каталоге проекта было 25 Python-скриптов и результаты прошлых экспериментов.
`tcp_closed_loop_pilot.py` отсутствовал; поиск также не обнаружил его в рабочем каталоге Codex.
Каталог не являлся Git-репозиторием. До изменения создан архив исходных файлов и результатов
с SHA256-манифестом в рабочем каталоге этого чата. Старые CSV/PNG не перезаписывались.

Основные зависимости:

```text
training_experiment -> Digits, MLP, симулятор размещения
joint_planning_experiment -> training, crypto_baseline, randomized_check
closed_loop_joint -> joint_planning, training, два протокола проверки
tcp_process_experiment -> tcp_verification_experiment -> два протокола
tcp_closed_loop_pilot -> tcp_runtime -> tcp_transport + существующая MLP + два протокола
```

## Найденные проблемы и изменения

| Проблема | Решение / статус |
|---|---|
| Заявленный новый TCP-пилот отсутствовал | Добавлен, с использованием существующей MLP и криптографических механизмов |
| `matplotlib>=3.7py` и отсутствующие sklearn/cryptography в requirements | Исправлены зависимости |
| Baseline складывал произвольные int64 без ограничения диапазона | Валидация до приведения типа и сложения, граница на каждый вход относительно числа участников |
| Baseline опирался на изменяемый глобальный размер вектора | Добавлены явные необязательные аргументы размера/числа блоков/границы; старый интерфейс сохранён |
| P имел жёсткий множитель 16 в `dot_mod`, зависел от глобальной границы | Динамические границы Worker/Verifier, безопасная арифметика, проверка неоднозначности modulo P |
| P позволял повторное использование объекта проверки | Одноразовая проверка; отдельные verifier в каждом негативном тесте |
| Неявное приведение float/uint64 и слабая проверка формата | Типы, длины, диапазоны, форма векторов и криптографический контекст проверяются явно |
| Исторический TCP принимал простой worker_id без аутентификации канала | Новый путь использует попарные HMAC-ключи, подписанные обновления/проекции и строгий envelope |
| Повторные запросы / старые раунды | Nonce replay cache, монотонные compute/aggregate, привязка проекции к текущему обновлению |
| Первая повреждённая реплика губила R в симуляторах | В новом TCP-пути перебор полученных комбинаций и реальная повторная криптопроверка |
| Принятый вектор мог быть спутан с тестовым эталоном | Новый coordinator собирает его только из edge-ответов; oracle существует только в тестах |
| Отсутствующий P-участник | Отказ проверки; B использует уже полученные подписанные обновления |
| Неопределённые зависания процессов | Абсолютные клиентские дедлайны, ограниченные socket operations, ограниченный startup, очистка дочерних процессов |
| Смешение CPU, локального TCP и WAN-модели | Новые метрики имеют отдельные определения; старые CALIB_MS не используются в TCP-пилоте |
| Сложение параллельных длительностей | Прямой таймер полного раунда и T_epsilon; стадии публикуются отдельно |
| Невоспроизводимые параметры и перезапись CSV | JSON-конфигурации, manifest исходников/версий, сценарии, уникальные директории |

## Что означают старые результаты

`joint_planning_experiment.build_learning_curve` вычисляет настоящие градиенты заранее,
проверяет обеими схемами, затем стратегии используют полученное число успешных шагов.
В `outcome` нет выполнения реальной криптографии: успех определяется состоянием симулятора.
Это корректно как модельный эксперимент, но не настоящее время обучения через TCP.

`closed_loop_joint.run_one` действительно вычисляет градиенты текущей модели и вызывает
выбранный протокол. Контрольный `updates.sum()` находится после криптопроверки и служит
assert-оракулом, а не источником принятого вектора. `network_delay` всё равно заменяет
физическое время и дедлайн модельной величиной. `crypto_cpu_seconds` там измеряется
`perf_counter`, то есть это wall-time последовательной локальной криптографии, не CPU-time.

Оба исторических симулятора выбирают только первую реплику. Их старое поведение сохранено
как историческая модель, чтобы не менять смысл уже сохранённых результатов. Исправленная
реализация резервирования находится в новом TCP-пути; сравнивать цифры как одну серию нельзя.

`CALIB_MS` взяты из измерений localhost TCP, поэтому содержат передачу, сериализацию и
ожидания, а не только CPU. Дополнительное WAN-слагаемое в старой модели даёт гибридную
стоимость с риском двойного учёта части локального транспорта. Значения для 12 участников
были приблизительными. Отдельный `check_joint_latency.py` проверяет арифметику формулы,
но не валидирует физическую точность калибровки. Передача агрегированной суммы в текущей
формуле уже включена и для B, и для P. Ретроспективно менять CSV некорректно.

`tcp_process_experiment.py` запускает отдельных участников, но исходные обновления и
готовая сумма созданы родителем до измерения. Это проверка протокола передачи и проверки,
а не закрытый цикл обучения. TCP worker_id там не криптографически аутентифицирован,
а `recv_exact` ограничен socket timeout отдельных вызовов, а не единым дедлайном сообщения.
Новый пилот использует отдельный строгий транспорт; исторический эксперимент сохранён.

## Принятые инженерные ограничения

Простой RPC создаёт новое TCP-соединение на запрос; persistent connections, раннее завершение
резервирования и отмена незавершённых RPC пока не реализованы. Они могут уменьшить накладные
расходы, но изменят измеряемый протокол. Тайм-аут на стороне Python не прерывает уже начатый
нативный BLAS-вызов; принятие просроченного обновления запрещено, при закрытии зависший
дочерний процесс завершается принудительно.

Сценарии отказа/подмены и нагрузочные ожидания задаются до запуска и скрыты от планировщика.
Обучение алгоритма по реальным временам не делает эксперимент детерминированным по wall-clock.
Настоящая защищённая передача между хостами и исследование сетевых ограничений — следующий
этап, не реализованный результат этой версии.

## Обнаруженная чувствительность обучения

Первая длинная серия использовала общий seed 12026 для сценария и весов модели.
Уже после четырёх обновлений при 4 участниках validation loss вырос до 6.105729,
а следующий градиент превысил допустимую границу 200000. Все схемы правильно
отклоняли дальнейшие обновления. Серия остановлена; её исходные измерения сохранены
в `results/tcp_closed_loop_20261027T002503Z_5c5f0d49/` со статусом прерванного запуска.

Seed модели отделён от seed сценария. Сравнение планировщиков далее условно на исходной
модели 2026, как в историческом эксперименте, и новых сценариях с базовым seed 12026
(генератор сценария использует 13026 + номер повтора). Это не проверка
обобщения на разные начальные веса. Контрольный последовательный прогон исходной MLP
подтвердил достижение loss≤0.22 на 35-м успешном обновлении при 4, 8 и 12 участниках.
При изменении инициализации нужны отдельный анализ устойчивости обучения и заранее
зафиксированные гиперпараметры; скрыто менять learning rate или обрезать градиенты нельзя.

## Завершённая проверка

Последовательные smoke-серии: по 30/30 успешных раундов на 4, 8 и 12 участниках.
Основная серия `tcp_closed_loop_20261027T002732Z_e0e5ce9c`: 360 запусков стратегий,
все достигли порога; 14 336 раундов, 12 600 принятых обновлений, ноль тайм-аутов.
Во всех раундах совпали счётчики прикладных tx/rx байтов. Хеши исходников совпали
с манифестом запуска; старые CSV/PNG совпали с исходным SHA256-манифестом.

Пройдены 27 unittest-тестов (4.312 s в итоговом запуске) и исторические
`aggregation_selftest.py`, `check_joint_latency.py`, `crypto_baseline.py`,
`randomized_check.py`; `pip check` успешен. После завершения не осталось
дочерних процессов эксперимента. Повторная проверка на другом компьютере
не выполнялась; этот запуск уже выполнен на текущем Mac пользователя.
