# Проверка PD-LinUCB против реактивного резервирования

Этот этап продолжает диагностику условий выигрыша. Цель — проверить, помогает
ли обучение различать устранимые и неустранимые резервом отказы при фиксированном
бюджете. Основой стенда остаются OCP-FL и исходный PD-LinUCB. Реактивные правила
добавлены как обязательные контрольные политики; они не заменяют алгоритм по умолчанию.

## Что реализовано

- Сценарий `mixed_availability` с заранее сохранённой последовательностью
  `healthy`, `edge`, `participant`. В первом случае ошибок не вводится. Во втором
  отказывает основной агрегатор, если приглашён клиент из целевой группы.
  В третьем один из выбранных OCP участников вычисляет обновление, но не отдаёт
  обязательное доказательство случайной проекции. Даже резервирование агрегатора
  не может заменить его участие. Здесь не моделируется полный отказ процесса клиента.
- Правило `reactive_edge` включает R+P после ошибки агрегатора. `reactive_any`
  включает R+P также после отсутствующего доказательства участника. Оба используют
  только предыдущие наблюдаемые ошибки, сохраняют кредит на каждый будущий раунд
  и расходуют оставшуюся квоту резерва, когда она покрывает весь остаток горизонта.
- Независимый аудитор восстанавливает решения этих правил отдельным расчётом
  доступного числа резервных запусков. Сохранены точный учёт кредитов, задержка
  наград, проверка списка OCP и воспроизведение траектории модели.
- `ocp_budget_report` проверяет сравнения до остановки по бюджету/горизонту.
  Отчёт до первого достижения качества остаётся отдельным (`ocp_compare_report`).
- `ocp_availability_sim` сравнивает исходный PD, абляции признаков, LinUCB,
  реактивные правила и фиксированную равномерную смесь.

## Заранее зафиксированный TCP-пилот

Два новых seed модели и списков OCP: 22 и 23. По 120 попыток, 174 кредита,
F+P стоит 1, R+P — 2. Награда — 1 за принятое обновление, 0 за непринятое.
Задержка награды — два раунда. alpha=1, ridge=1, eta=0,05 у PD.
OCP выбирает 3 из 6 клиентов. Digits/MLP, hidden=64, learning rate=0,5.
Остановка по validation loss отключена. Первичный показатель — число принятых
обновлений до остановки, вторичные — конечный validation loss и gas.

Трассы созданы до запусков через `random.Random(10000 + seed)`. С вероятностью
0,8 сохраняется прошлый тип состояния, иначе выбирается новое с вероятностями
0,40 / 0,35 / 0,25. Это вероятности генератора, а не доли в конкретной конечной
трассе. Сценарий не передаётся планировщику. Доступны только ошибки предыдущего
раунда и награды выбранного действия. Задержка телеметрии и награды различаются:
ошибки прошлого раунда доступны сразу перед следующим, метка награды — через два.

Порядок политик зафиксирован: reactive_edge, pd_projection, reactive_any, spread.
Все политики начинают с чистого состояния и холодного кэша проверки BLS.
Время сохраняется для диагностики. Сравнение не предназначено для вывода о скорости.
Используются локальные TCP-процессы, EthereumTester/PyEVM и BLS-маяк с тестовым ключом.

## Результаты TCP-пилота

Завершены все восемь запусков, всего 959 реальных раундов. Аудит проверил
сертификаты OCP, совпадение списков на общих префиксах, решения политик,
отложенные метки, кредитный учёт, транзакции и траектории модели. Во всех раундах
исход совпал со структурной моделью инъекций. Дополнительных потерь от дедлайнов
в этой серии не выявлено. Исполняемые ядра и адаптеры одинаковы во всех четырёх
политиках по SHA-256; исходники сохранены отдельно в каждом запуске.

Все политики израсходовали 174 кредита. Ни одна не достигла validation loss 0,22.

## Отдельные проверки четырёх действий

Основной TCP-пилот выше изолирует резервирование и использует F+P/R+P.
Отсутствие доказательства P не является полной недоступностью клиента:
F+B может принять его уже подписанное полное обновление. Поэтому провели
дополнительную симуляционную серию с четырьмя действиями на seed 9000–9047.
`reactive_joint` выбирает F+B после отсутствующего P-доказательства и R+P после
ошибки агрегатора; при отсутствии этих сигналов сохраняет дешёвый режим и
расходует остаток квоты в конце. Проверка бюджета остаётся жёсткой.

Телеметрия зависит от действия. Если выбран B, отсутствие P-доказательства
не наблюдается и не попадает в следующий контекст. Симулятор не передаёт
скрытый тип отказа под видом наблюдения. Простой контроль не запоминает
ненаблюдённый статус P после B. Контроль с памятью и специально выделенными
проверочными раундами остаётся дополнительным сильным соперником для будущего.

При B=174 и смешанных отказах средние принятые обновления:

| ρ | PD, два режима | PD, четыре режима | Реактивный выбор проверки и резерва |
| ---: | ---: | ---: | ---: |
| 0 | 71,19 | 70,27 | 69,77 |
| 0,50 | 73,10 | 74,79 | 83,98 |
| 0,85 | 76,17 | 80,25 | 92,29 |

Четыре действия действительно полезнее двух при предсказуемых смешанных сбоях.
Но обучение по-прежнему уступает простому правилу с известной связью между типом
отказа и способом восстановления. При независимых сбоях небольшая положительная
разница не устанавливает превосходство. Все 18 ячеек и 8640 траекторий сохранены.
Это симуляция, а не четыре новых TCP-политики.

## Проверенная модификация с общими параметрами

В `structured_pd_linucb.py` реализован экспериментальный общий линейный прогноз:

`E[r | x,a] ≈ beta_0 @ x + I_R(a) * beta_R @ x + I_B(a) * beta_B @ x`.

Действие описывается признаками `[x, I_R*x, I_B*x]`. Одна ridge-модель переносит
информацию между режимами. Учитывается полная общая ковариация, а не сумма
независимых доверительных интервалов. Кредитный учёт, двойственная цена и порядок
обновления геометрии/отложенных меток сохранены. Обучение использует только награду
выбранного действия; контрфактические метки не добавляются.

Общие параметры для разных действий — каноничная идея
[LinUCB с общими/гибридными признаками](https://www.schapire.net/papers/www10.pdf),
раздел 3.2. Наша версия использует полностью общий вектор, без дополнительных
отдельных остатков по действиям. Это проверяемая модификация постановки, а не
заявка на новизну самой идеи. Её аддитивность может нарушаться при одновременных
отказах и взаимодействии размещения с проверкой; тогда нужен член взаимодействия
или отдельные остатки. Гарантии статьи PD-LinUCB автоматически не переносятся.

После первых двух исследований до новых исходов зафиксирована третья серия
seed 10000–10047 с теми же сеткой, alpha, ridge, eta и задержкой. Дополнительный
контроль `pd_joint_compact` имеет те же пять наблюдаемых признаков, что общий
вариант: константа, две прошлые ошибки, предыдущее резервирование и предыдущий B.
У него четыре независимые модели. Это отделяет эффект общих параметров от простой
замены контекста. Для общей модели получается 15 коэффициентов, для независимого

гипотез в заранее зарегистрированное подтверждающее исследование.

## Интерпретация и следующий шаг

При ρ=0 наблюдаемые прошлые ошибки не предсказывают текущий отказ. Ожидаемая
прибавка от резерва постоянна и равна 0,35 × 0,8 = 0,28. При используемых
вероятностях оптимальное ожидаемое распределение расходов в этой простой модели
покрывает полный горизонт и тратит остаток на резерв. Избирательное включение
резерва по прошлой ошибке тогда не имеет информационного преимущества.

При ρ>0 признак прошлой ошибки полезен. Однако реактивное правило заранее знает,
какой тип отказа устраняется резервом. PD сначала изучает эту связь и исследует
альтернативы. Текущая проверка показывает пользу адаптивного резервирования
относительно смеси, но не подтверждает преимущество обучения перед знанием
структуры задачи.

Ближайший содержательный эксперимент — включить проверенный состав OCP в контекст
планировщика. Сейчас он получает количество выбранных клиентов, а их идентичности
не использует, хотя сертификат уже доступен до решения. Допустимы признаки состава
или фактической нагрузки маршрутов, известные из системы. Недопустимо добавлять
признак «приглашён атакуемый клиент», вычисленный по скрытой разметке инъекции.
Нужно проверить, учится ли метод на наблюдаемых исходах различать риск составов,
при одинаковой информации у сильного контрольного предиктора.

Следующий план фиксируется до новых запусков:

1. Расширить контекст проверенным составом и причинно доступной телеметрией
   основного и резервного маршрутов. Отдельно измерить возраст и пропуски данных.
2. Ввести практически обоснованные случаи, где резерв может быть недоступен или
   не уложиться в дедлайн, и случаи, где он действительно спасает раунд. Сохранить
   здоровые и непредсказуемые сценарии как отрицательные контроли.
3. Сравнить исходный PD, PD с расширенным контекстом, `reactive_edge`, предиктор
   риска с теми же признаками и фиксированные политики на одинаковых ресурсах.
4. Настройку делать на отдельной серии. Заранее выбрать один основной контраст
   против сильного контроля и проверить его на новых seed, сохраняя все поражения.
5. Рассматривать оценку дополнительной пользы действия или консервативную
   коррекцию базового правила только после проверки, что новые признаки полезны.

## Другие каноничные направления и границы новизны

У двух действий исходный PD уже выбирает R, когда

`(mu_R - mu_F) + alpha * (sigma_R - sigma_F) > dual * (c_R - c_F)`

с учётом допустимости по бюджету и правила разрешения ничьей. Поэтому простая
перепись решения в терминах «дополнительной пользы» не создаёт нового алгоритма.
Отдельная оценка эффекта резерва с общей базовой частью награды — более существенное
изменение. Каноничная опора — [Action Centered Contextual Bandits](https://proceedings.neurips.cc/paper/2017/hash/4fa177df22864518b2d7818d4db5db2d-Abstract.html)
и [Semiparametric Contextual Bandits](https://proceedings.mlr.press/v80/krishnamurthy18a.html).
Для такого переноса нужны рандомизация, журнал вероятностей выбора и корректная
работа с принудительными бюджетом действиями. Текущий детерминированный журнал
не позволяет просто подставить propensity-веса. Их результаты не доказывают
гарантии для нашего сочетания бюджета, задержек и отказов.

Второй путь — использовать сильное базовое правило и изучать улучшение над ним.
[Conservative Contextual Linear Bandits](https://papers.nips.cc/paper_files/paper/2017/hash/bdc4626aa1d1df8e14d80d345b2a442d-Abstract.html)
формализует ограничение потерь относительно базовой политики. Перенос такого
подхода потребует отдельного обоснования при общем расходуемом бюджете и
отложенных метках. Сейчас гарантии «не хуже правила» у стенда нет.

Ресурсная постановка соответствует направлению
[Linear Contextual Bandits with Knapsacks](https://proceedings.neurips.cc/paper_files/paper/2016/hash/f3144cefe89a60d6a1afaf7859c5076b-Abstract.html).
Добавление gas как отдельного ресурса требует проверки верхней границы стоимости
полного следующего раунда до открытия церемонии. Двойственный штраф не заменяет
такую проверку. Кредиты исполнения и gas нельзя складывать без явной модели цены.

Потенциальный исследовательский вклад — адаптация исполнения к проверяемому составу
OCP при задержках и ресурсах, с измеренной выгодой относительно сильного правила.
Текущая серия не устанавливает такую новизну и не подтверждает универсальный
выигрыш PD-LinUCB. Кандидат с тремя признаками не переносится в основной планировщик
в отсутствие преимущества.

## Воспроизведение

```bash
OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 .venv/bin/python -m adaptive_planning.ocp_compare \
  --config configs/tcp_ocp_mixed_availability.json \
  --output results/ocp_mixed_availability \
  --restricted-bandits --scheduled-controls --reactive-controls \
  --policies reactive_edge pd_projection reactive_any spread

.venv/bin/python -m adaptive_planning.ocp_budget_report \
  results/ocp_mixed_availability --output results/ocp_mixed_availability_report

OPENBLAS_NUM_THREADS=1 .venv/bin/python -m adaptive_planning.ocp_availability_sim \
  --output results/ocp_mixed_simulation

OPENBLAS_NUM_THREADS=1 .venv/bin/python -m adaptive_planning.ocp_availability_sim \
  --joint-controls --seed-start 9000 --output results/ocp_joint_mode_simulation

OPENBLAS_NUM_THREADS=1 .venv/bin/python -m adaptive_planning.ocp_availability_sim \
  --shared-model --seed-start 10000 --output results/ocp_shared_model_simulation
```

Каталоги результатов должны быть новыми. Завершённую серию сравнения можно
продолжить с `--resume`, сохранив конфигурацию, состав и порядок политик.

## Проверки и сохранённые материалы

Итоговый набор — 143 успешных теста. Среди новых проверок: невозможность
перерасхода у реактивных политик, независимый пересчёт их решений, совпадение
симуляции PD с TCP-адаптером, отсутствие зависимости текущего выбора от текущей
или будущей инъекции, ненаблюдаемость отсутствующих P-доказательств в режиме B,
пакетное воспроизведение ridge-матрицы общего варианта и реальная TCP-проверка,
что F+B принимает обновление при отказе P-доказательства. Ruff проверен.

В `results/` сохранены:

- `ocp_mixed_availability` — конфигурация, журналы TCP/OCP/EVM, исходники каждого запуска;
- `ocp_mixed_availability_report` — аудит, таблицы по seed и средние;
- `ocp_mixed_simulation` — первая сетка двух режимов, исходники и полный график отличий;
- `ocp_joint_mode_simulation` — отдельная сетка четырёх действий;
- `ocp_shared_model_simulation` — проверка общих параметров и двух контролей;
- `ocp_mixed_availability_stage` — зафиксированный план, генератор трасс и журнал тестов.

Все три симуляционные серии разведочные. Ни сокращение признаков, ни общие
параметры не приняты как подтверждённое улучшение метода. Отрицательные результаты
сохраняются вместе с положительными сравнениями против фиксированной смеси.
