# Изменяющиеся ограничения передачи и причинное планирование

Этот этап проверяет адаптацию между раундами настоящего TCP-обучения. Условия сети
меняются после 4–8 попыток: то общий поток worker→edge, то общий вход проверяющего
ограничен 40 MB/s. Задержка прикладного сообщения в обоих режимах равна 2 ms.
Внутри раунда профиль фиксирован. Трасса индексируется попытками, не физическим временем.

## Предварительно заданный протокол

Первичный контраст: **network_online − network_rule** по физическому T_epsilon.
Отрицательная разность означает выигрыш онлайн-планировщика. Сравнение с прежними
планировщиками и четырьмя фиксированными действиями — вторичные описательные контрасты.

- Основная серия: 12 участников, 12 парных повторов, 8 стратегий, до 80 попыток.
- Исходная MLP: seed 2026, 50260 параметров, target validation loss 0.22.
- Основной seed 43026; повтор r использует 43026+r.
- Fault RNG: seed+1000; профиль сети: seed+2000; прежний planner: seed+10000;
  новый planner: seed+11000; перестановка стратегий: seed+20000.
- Предварительные инженерные трассы: seed 33026, два повтора; smoke: seed 33026,
  чистый сценарий, профиль меняется каждую попытку, 4/8/12 участников.
- Дедлайн раунда 1.5 s, timeout RPC 1.2 s, ожидание переключения 0.025 s.
- Парные разности считаются на одинаковом номере повтора. Bootstrap среднего:
  20000 выборок, seed анализа 143026. Интервалы описательные; мощность не рассчитана.
- Недостигнутый порог остаётся пустым T_epsilon, показывается доля достижения;
  основной bootstrap только по полным парам не устраняет смещение при цензурировании.
- Все параметры задаются до просмотра основной серии. Изменения алгоритма после
  её просмотра потребуют новых независимо заданных проверочных трасс.

Фиксированная инициализация модели означает, что эта серия не проверяет обобщение
на другие начальные веса. Прежняя неудачная инициализация сохраняется в старых результатах.

## Одинаковая доступная информация

Новые стратегии получают frozen `Observation`: число участников, длину вектора,
текущие объявленные ограничения трёх направлений, задержку и прошлые наблюдённые
проблемы edge/P. Объект не содержит трассы, будущих отказов, длительности фазы
или номера следующего переключения. Это идеализированная мгновенная телеметрия
конфигурации, а не оценка фактической скорости по шумным измерениям.

`network_rule` выбирает минимальную приблизительную стоимость, включая текущую
цену переключения. После наблюдённой edge-ошибки использует резерв, после отсутствия
необходимого участника P — B. Ошибка доступности P не классифицируется как плохая edge-реплика.

`network_online` использует тот же расчёт передачи как prior, оценивает вероятность
успеха выбранного действия и среднее остаточное время. Exploration 5%. Начальная
Beta-оценка успеха: (success+4)/(n+5). Остаточное время имеет два условных наблюдения:
0.030 s + 0.005 s для P + 0.006 s для R. Эти небольшие константы задают грубый
масштаб прежней localhost-серии и не являются новой калибровкой.

В расчёте передачи R возвращает две суммы, а не одну. Для P дополнительно учтены
малые подписанные ответы и два сообщения интерактивного этапа. Формула — приблизительный
prior; перекрытия, TCP, framing и CPU в ней неполны. Приём результата и итоговое
время определяются только реальным протоколом и физическими таймерами.

Обратная связь обновляет только выбранное действие. Из cycle time вычитается
фактическое ожидание переключения и известная приблизительная стоимость передачи;
положительный остаток усредняется. Цена следующего переключения добавляется при выборе
один раз. Оценки не дают гарантий оптимальности; отрицательный результат допустим.

## Привязка профиля к раунду

В `NetworkShaper` добавлена общая для spawn-процессов таблица профилей по номеру
раунда. Запись делает launcher до отправки команд, она неизменяема. Позднее сообщение
раунда r использует профиль r, даже после начала r+1. Общие pacer-очереди сохраняются,
поэтому смена профиля не обнуляет уже зарезервированный бюджет передачи.

Таблица содержит 65536 позиций, без циклического переиспользования: допустимы номера
1..65535. Конфигурация проверяет верхнюю границу числа раундов вместе с прогревом.
Статические эксперименты продолжают использовать прежний путь и свои профили.

Проверка принудительного завершения процесса выявила, что multiprocessing.Lock
может оставаться занятым после смерти владельца. Ожидание блокировки конфигурации
теперь ограничено оставшимся дедлайном и максимумом 0.5 s. Это защищает от
бесконечного ожидания; автоматическое восстановление осиротевшей блокировки
не реализовано, такой кластер потребуется перезапустить.

Первая незавершённая основная серия protocol revision 1 была остановлена после
воспроизведения этого сбоя в отдельной проверке. Её данные сохранены отдельно,
не объединяются с основной повторной серией revision 2. Код алгоритмов, seed и
параметры оценки при исправлении не менялись. Цель исправления — ограничение
ожиданий, не подбор результата планировщика.

## Запуск и файлы

```bash
.venv/bin/python -m unittest discover -s tests -v
.venv/bin/python tcp_dynamic_experiment.py --config configs/tcp_dynamic_smoke.json
.venv/bin/python tcp_dynamic_experiment.py --config configs/tcp_dynamic_smoke.json --workers 8
.venv/bin/python tcp_dynamic_experiment.py --config configs/tcp_dynamic_smoke.json --workers 12
.venv/bin/python tcp_dynamic_experiment.py --config configs/tcp_dynamic_development.json
.venv/bin/python tcp_dynamic_experiment.py --config configs/tcp_dynamic_eval.json
```

Создаются новые `results/tcp_dynamic_<stage>_<UTC>_<id>/` с metadata,
source_snapshot.zip, JSON-трассами, CSV и JSONL-журналами каждой попытки.
Журналы записываются и flush-ятся после каждого раунда; при обычном прерывании
сохраняются уже записанные попытки незаконченной стратегии. Восстановление модели
из журнала и гарантия сохранности при отключении питания пока не реализованы.

Анализ завершённой серии:

```bash
.venv/bin/python tcp_dynamic_analyze.py results/ИМЯ_СЕРИИ --output outputs/НОВЫЙ_КАТАЛОГ
```

T_epsilon включает непрерывное время выбора, выполнения, предыдущих validation,
телеметрии и журналирования. Startup, начальная validation и одинаковый прогрев
исключены. Суммы параллельных стадий не заменяют полный таймер.

## Ограничения

Это прикладной pacing на одном Mac. Не проверяются WAN, шум и задержка телеметрии,
изменения полосы посреди передачи, неодновременные градиенты и сговор участников.
Поскольку фазы привязаны к попыткам, стратегии могут достичь порога на разных
фазах и после разного числа отказов. Это воспроизводимое попарное сравнение
политик на общей трассе попыток, а не одно общее физическое расписание сети.

## Независимая проверка вклада обучения

До анализа основной серии отдельно задана проверка с seed 53026 и восемью парами:
`network_online`, `network_prior`, `network_rule`. Первичный контраст этой проверки —
network_online − network_prior. Её данные не объединяются с основной оценкой.

`network_prior` использует тот же класс выбора, начальные значения, exploration 5%
и RNG, что network_online. Отличие одно: observe() ничего не меняет. Это отключает
обучение планировщика; нейросеть продолжает обучаться по реальным проверенным
градиентам. Показатель feedback_updates для network_prior должен оставаться нулём.
Псевдослучайные пробы на общем префиксе попыток совпадают у двух алгоритмов.

```bash
.venv/bin/python tcp_dynamic_experiment.py --config configs/tcp_dynamic_ablation.json
```

Цель — проверить, не объясняется ли результат сильным аналитическим prior без
пользы обновления статистики. Код исходного NetworkOnlinePlanner при добавлении
этой проверки не изменяется; frozen-вариант только наследует его и отключает observe.
