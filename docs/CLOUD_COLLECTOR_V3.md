Актуальная инструкция версии 0.6.0 для Timeweb находится в [deploy/timeweb/RUNBOOK_RU.md](../deploy/timeweb/RUNBOOK_RU.md). Ниже сохранены команды и ограничения предыдущего выпуска.

# Облачные эксперименты с collector v3

## Одна Linux-ВМ

Этот вариант воспроизводит архивный анализ и запускает настоящие TCP-процессы и локальную EthereumTester EVM на облачной машине. Подойдёт Ubuntu с Python 3.13. Сначала выполните установку из корневого README. Для стабильности измерений ограничьте потоки BLAS

```bash
export OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 MKL_NUM_THREADS=1
export MPLBACKEND=Agg
mkdir -p results
git rev-parse HEAD > results/source-commit.txt
python experiments/collector_v3/kit/analyze_v3.py \
  experiments/collector_v3/data results/reproduced.json
cmp experiments/collector_v3/data/summary.json results/reproduced.json
```

Полный повтор расчётов по матрицам

```bash
python experiments/collector_v3/kit/replay.py \
  . experiments/collector_v3/data results/replay-v3
```

Новый локальный TCP/EVM-прогон внутри ВМ

```bash
mkdir -p results/live-v3
cp experiments/collector_v3/data/gateway_calibration.json results/live-v3/
cp -R experiments/collector_v3/data/atlas results/live-v3/
python experiments/collector_v3/kit/live.py . results/live-v3 --cached-finality
python experiments/collector_v3/kit/live.py . results/live-v3 \
  --atlas --rounds 24 --seeds 37101 --modes joint no_ids recent
```

Первая команда исполняет четыре серии по 48 раундов для шести правил. Вторая использует первые 24 окна первой группы A с четырьмя работниками. Результаты записываются в `live/` и `live_atlas/`. Существующие завершённые эпизоды пропускаются. Для независимого повтора используйте другую папку. В этих опытах задержки путей исполняются стендом, а локальный маяк и EVM служат исследовательской проверке.

Скрипт не расходует баланс внешнего блокчейна. Измерение сетевого этапа начинается после проверки сертификата и бронирования. Для публикации облачного результата отдельно измерьте полное время от начала раунда, включая получение финальности и разрешения.

## Несколько машин

Существующие роли запускает `adaptive_planning.distributed.RemoteCluster`, используя SSH, реальную TCP-сеть и общие временные дедлайны. Для этих ролей требуется `ADAPTIVE_CLOCK=wall` и синхронизация часов. Установите одну ревизию проекта на координатор и все машины worker/edge.

Шаблоны `deploy/yandex/` создают координатор, worker-ВМ и четыре edge-ВМ. Параметры задаются в копии `terraform.tfvars.example`. План и стоимость инфраструктуры проверяются оператором до `terraform apply`. Команды развёртывания и старого облачного пилота описаны в [существующей инструкции](../deploy/yandex/RUNBOOK_RU.md).

`deploy/live_study.py` запускает прежний факторизованный пилот. Текущий `experiments/collector_v3/kit/live.py` создаёт локальный Cluster. Для распределённой проверки нового выбора шлюзов требуется подключить его к RemoteCluster и реализовать пункты 2, 4 и 5 задания из отчёта. Общий жёсткий счётчик байтов в текущем RemoteCluster работает только на одном хосте. В распределённом опыте собираются счётчики каждой роли, а атомарное межхостовое ограничение требует механизма резервирования.

## Что сохранять для статьи

Сохраните commit SHA и tag, план до просмотра исходов, типы ВМ, зоны, состав участников, версии Python и зависимостей, синхронизацию часов, настройки шлюзов и бюджеты. Логируйте бронирование до отправки, включая неудачные запросы, полный дедлайн, индивидуальные проверенные ответы, прикладные байты каждой роли, gas и хеши моделей.

В парных сравнениях у методов должны совпадать составы, доступные действия, исходная история, права наблюдения и квоты. Отдельно сравните нулевой бонус UCB, недавние отклики с теми же ценами, агрегатное обучение и раннюю бронь. Полное время ожидания новой брони особенно существенно при окнах 80–200 мс. Требования к очередям, меткам времени и внешнему аудиту перечислены в отчёте.
